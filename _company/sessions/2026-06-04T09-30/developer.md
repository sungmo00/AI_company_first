### 🛠️ 기술 구현 가능성 분석 체크리스트 (Action Plan 기반)

#### 섹션 1: Phase별 기술적 위험도 분석 (Technical Risk Assessment)

이 섹션은 Action Plan의 각 Phase별로 예상되는 기술적 난관을 식별하고, 이를 해결하기 위한 선제적 대응 방안을 정의합니다.

| Phase | 핵심 Task (from Action Plan) | 예상되는 주요 기술적 위험 요소 (Risk Factor) | 심각도 (1-5, 5=Critical) | 해결 방안 및 선제적 조치 (Mitigation Strategy) |
| :--- | :--- | :--- | :--- | :--- |
| **Phase 1: 기반 구축** | 타겟 기관/분야 매핑 최종 확정 | 비즈니스 목표와 직접적으로 연결되는 'Top N' 기준의 모호성. (정성적 판단) | 4 | 비즈니스 목표(ROI)와 가중치($W_1=0.5$) 간의 정량적 변환 로직 정의에 대한 명확한 합의 도출. |
| **Phase 2: 데이터 인프라 설계** | 최종 DB 스키마 및 API 인터페이스 확정 | 데이터 요구사항(13개 컬럼)의 비즈니스 실현 가능성 검토 실패. API 응답 구조의 복잡도. | 5 | **(필수)** Researcher가 정의한 Pydantic 모델 검토를 통한 데이터 필드 간 종속성 분석 및 최소 기능(MVP) 스키마 확정. |
| **Phase 3: 데이터 수집 및 검증** | MVP 데이터 수집 모듈 초안 구현 (PoC) | 크롤링/API 호출 시 발생하는 빈번한 오류(Rate Limiting, 구조 변경). 데이터 정제 과정의 비효율성. | 4 | **(필수)** 초기 PoC 단계에서 외부 서비스의 안정성 테스트(Stress Test) 및 에러 핸들링 로직을 최우선으로 구현. |
| **Phase 3: 데이터 수집 및 검증** | AMS 가중치 로직 적용 | 복잡한 다차원적 점수 계산 로직의 버그 유발 가능성. (특히 가중치 조합 오류) | 3 | 로직 분리(Separation of Concerns) 원칙 준수. 핵심 계산 모듈을 독립적으로 단위 테스트(Unit Test)하여 안정성 확보. |

| Phase | 핵심 Task (from Action Plan) | 예상 공수 (Man-Month, MM) | 주요 병목 구간 (Bottleneck) | 권장 리소스 배분 방향 |
| :--- | :--- | :--- | :--- | :--- |
| **Phase 1: 기반 구축** | Top N 기준 정량화 및 가이드라인 초안 작성 | 2 MM (연구원/기획) | 비즈니스 요구사항과 기술 로직 간의 Gap. | 기획/연구 리소스 집중 투입. (개발 리소스 최소화) |
| **Phase 2: 데이터 인프라 설계** | 최종 DB 스키마 및 API 인터페이스 확정 | 3 MM (개발/분석) | 데이터 모델링의 복잡도 및 관계 설정 오류. | **코다리 집중 투입.** (Schema Definition Generator의 안정성 확보에 중점) |
| **Phase 3: 데이터 수집 및 검증** | MVP 데이터 수집 모듈 구현 (PoC) | 4 MM (개발/QA) | 외부 API 안정성 및 데이터 정제 로직의 복잡성. | 개발팀 2인 투입, QA 리소스 병행 투입. (테스트 커버리지 확보 필수) |
| **Phase 3: 데이터 수집 및 검증** | AMS 가중치 로직 적용 구현 | 2 MM (개발/테스트) | 복잡한 가중치 계산 로직의 디버깅 시간. | 독립적인 모듈 개발 후, 통합 테스트 시 집중 공수 투입. |
